PYNQ-Zoom: A Reprogrammable Fractal Renderer

A real-time fractal rendering engine combining FPGA-accelerated escape-time computation with browser-based control. 48 parallel compute cores on a PYNQ-Z1 synthesise the Mariani-Silver algorithm in hardware, reaching 42 Mpixels/s, a 36× speedup over the on-board ARM Cortex-A9, while an ARM-hosted gateway streams rendered tiles to a browser frontend over WebSocket.

Built by a six-person team at Imperial College London. My contributions were the memory subsystem (colour BRAM, rotating state BRAM, tile table), the background BRAM-to-DRAM streaming pipeline, the queue system (generic FIFO underlying the job and complete queues), the top-level control (sixteenth-sequencing state machine), and the randomised RTL testbench suite used across integration testing.

Overview

PYNQ-Zoom renders the Mandelbrot set, Julia sets, and 30 other escape-time fractal variants in real time on a PYNQ-Z1, using a hardware implementation of the Mariani-Silver algorithm: a quad-tree traversal that flood-fills any region whose border pixels share one colour, and only recurses into sub-quadrants where the border disagrees. 48 parallel compute cores iterate z = z² + c directly in programmable logic, each switching at runtime between an 18-bit narrow mode (two pixels per core, per cycle) and a 35-bit wide mode for deep zooms, reusing the same DSP slices across both. An ARM-hosted gateway configures the accelerator over AXI-Lite, reads the rendered frame back over AXI-HP, and streams it to a browser frontend over WebSocket, and the same accelerator is shared across concurrent users through MandelBrew, a silicon-as-a-service product layer with admission control, fair scheduling and a community gallery to wrap the project as a product.

Technical Approach: My Contributions

Top-level control

I designed the sixteenth_controller, the top-level state machine that sequences all 16 sub-images (“sixteenths”) of the 1024×1024 frame in row-major order. It cycles through four states: IDLE, LOAD, RENDER, and NEXT, latching configuration from the PS on a start pulse, releasing the per-sixteenth engine from reset, and detecting completion once all 256 tiles in that sixteenth have reached DDR, before advancing to the next sixteenth or signalling the full frame done.

Memory subsystem

I built the three on-chip memories each per-sixteenth engine uses. The colour BRAM packs eight palette-index pixels into each 64-bit word to match the AXI-HP beat exactly, so the streaming unit forwards words to DDR with no packing or width conversion; a per-tile write counter beside the write port flags a tile as done without ever having to scan memory. The state BRAM tracks two-bit unvisited/queued/done status per pixel for the quad-tree traversal, using a four-bank rotating scheme rather than a two-bank ping-pong: one bank active per sixteenth while the other three clear in the background, which guarantees a clear spare bank even when a run of sixteenths flood-fills near-instantly, and eliminated the state-memory drain tail entirely (down to 0 cycles from a non-zero figure under the two-bank design). The tile table is a flat register file (not a BRAM, since it needs a same-cycle multi-tile write and a combinational read) recording which tiles were flood-filled and with what colour, linking the scheduler's fill decisions directly to the streaming unit.

Background BRAM-to-DRAM streaming pipeline

I built the streaming unit that drains completed tiles from the colour BRAM to DDR over AXI-HP, running independently of the compute pipeline so streaming never stalls rendering. For flood-filled tiles, it reads the tile table combinationally and synthesises constant-colour words directly, skipping a colour-BRAM read entirely, since a uniform region never needed its interior computed in the first place. A two-slot FIFO between the BRAM read and the AXI write hides read latency and absorbs short stalls, holding rather than dropping data under backpressure. I also replaced a 1024-input priority-encoder chain for selecting the next completed tile (which capped Fmax by scaling logic depth linearly with tile count) with a balanced reduction tree, taking tile-selection frequency from 72 MHz to 158 MHz. Restructuring the scan and address-generation stages to overlap with the previous tile's AXI handshake, and batching writes into 16-beat AXI bursts, cut the total drain-tail cost across all 16 sixteenths.

Queue system

I designed the generic parameterised FIFO (DATA_WIDTH, DEPTH) underlying both cross-stage queues in the pipeline: the job queue (scheduler → control unit, depth 256, carrying border-pixel coordinates plus a first-time-queued flag) and the complete queue (control unit → comparator, depth 2, carrying finished pixel results). Each is a circular buffer whose read/write pointers carry one extra bit so full/empty can be distinguished without an occupancy comparator on the critical path, plus a synchronous single-cycle flush. I also added an almost_full flag, asserted one slot early, after testing showed the job queue's registered valid output meant an in-flight pixel was already dropped by the time full was observed.

Randomised RTL testbench suite

I built out the Icarus-based testbench infrastructure used across the project's integration testing, following a UVM-influenced driver/monitor/scoreboard split even in the lightweight simulation flow: a behavioural stub at every module boundary, randomised and directed stimulus driven through a dedicated task, and outputs checked against a golden reference before a $display-based pass/fail verdict, runnable headlessly in CI. This caught real integration bugs before hardware bring-up, including a concurrent-write conflict in the BRAM-to-DRAM FIFO update logic that silently overwrote one data word per tile under certain arbitration timing.

Results

  • 42 Mpixels/s render throughput, 42 FPS at 1024×1024, across 48 parallel cores: a 36× speedup over the ARM Cortex-A9 baseline.
  • BRAM-to-DRAM drain-tail cut to 56 across all 16 sixteenths (roughly three orders of magnitude) via overlapped scan/check, single-cycle tile-table reads, and AXI burst writes.
  • Tile-selection critical path improved from 72 MHz to 158 MHz by replacing a naive priority-encoder chain with a balanced reduction tree.
  • Four-bank rotating state BRAM eliminated the state-memory clear tail entirely (0 cycles), removing a bottleneck the original two-bank ping-pong design was exposed to.
  • Job-queue backpressure fix (the almost_full lookahead) eliminated dropped border pixels under load, resolving a bug that had been hanging the scheduler.

Full system-level detail, including the scheduler's quad-tree traversal, the dynamic-precision compute cores, and the multi-client MandelBrew product layer built by the rest of the team, is in the project report.

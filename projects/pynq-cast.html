PYNQ-Cast: A Multiplayer Raycasting Engine on PYNQ FPGA

A multiplayer first-person raycasting game engine, packaged with a cloud-hosted development and hosting platform. PYNQ-Z1 FPGA nodes render scenes entirely in hardware and synchronise over UDP with a cloud-authoritative AWS EC2 server, which also exposes a browser-based development environment for map editing, session management, and replays.

Built by a seven-person team at Imperial College London. My contributions were the HDMI output protocol, removing Xilinx's VDMA-based display pipeline in favour of a direct AXI-Stream path, and the hardware UI overlay system, a general-purpose compositing layer for text, textboxes, and loading bars.

Overview

PYNQcast is a multiplayer first-person raycasting engine spanning two or more PYNQ-Z1 FPGA nodes and an AWS EC2 server. On each node, the FPGA fabric runs a hardware DDA (Digital Differential Analyser) raycasting engine that outputs directly to HDMI, while the onboard ARM Cortex-A9 handles input, tracks player position and camera angle, and syncs state with the server over UDP. A shared BRAM bridges the two. The server is authoritative for all game state: it resolves collisions, broadcasts unified state back to every node each tick, and exposes a browser-based environment for map editing, session management, and match replay.

Technical Approach: My Contributions

HDMI output protocol

The stock PYNQ video overlay writes each frame to a DDR3 framebuffer, then reads it back through VDMA before it reaches the display pipeline. That costs 900 kB of AXI traffic per frame and around 55 MB/s of bandwidth at 60 fps, and it lets frame rate couple to PS scheduling, with tearing possible if the display scans out a frame the PS is still writing. I removed VDMA entirely: the raycaster's AXI-Stream output connects directly into the video timing chain, so there is no shared framebuffer for tearing to occur on, and frame rate is governed purely by hardware. End-to-end pixel latency drops from 16.7 ms to under 1 microsecond, the full 55 MB/s of AXI bandwidth is freed for networking, and the ARM core just writes a game-state packet to BRAM each tick rather than managing DMA transfers. After a full rewrite, the video timing and HDMI encoder IP costs about 1,800 LUTs and no BRAM.

Hardware UI overlay

I built a general-purpose compositing layer so the raycast render can carry a HUD without any bitstream changes between applications, just different register values written by the PS at startup. Two IPs sit in the pixel stream. A textbox block evaluates axis-aligned rectangle slots fully in parallel, each pixel clock, with a priority mux picking the first hit and one register stage of latency; loading bars reuse the same evaluation, driven by a fill amount from the PS. A text overlay reads a glyph BRAM covering the printable ASCII set, resolving position to a BRAM address, a fetched byte, and a single-bit pixel gate in one clock cycle. The glyph BRAM doubles as a general sprite tile store, so the PS can upload a custom bitmap at runtime through the same one-cycle path. Together the overlay IPs cost around 180 LUTs and one BRAM tile, against roughly 55 MB/s of AXI bandwidth a software equivalent would need at 480p.

Results

  • End-to-end pixel latency cut from 16.7 ms to under 1 microsecond by removing VDMA from the display path.
  • Full 55 MB/s of AXI bandwidth recovered from the display pipeline and made available to networking.
  • UI overlay system: around 180 LUTs and 1 BRAM tile, versus roughly 55 MB/s of AXI bandwidth a software overlay would need at 480p.
  • Whole-system raycaster runs at under 10% of its throughput budget at 60 FPS, with PL resource use around 20% overall, leaving headroom for the overlay and future extensions.

Full system detail, including the DDA raycasting core, sprite and texture rendering, and the server-side SEDA-inspired reactor architecture built by the rest of the team, is in the project report.
